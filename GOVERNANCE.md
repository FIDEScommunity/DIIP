# DIIP Governance

This document outlines the governance structure and processes for the Decentralized Identity Interop Profile (DIIP) specification.
The Governance model is simple, transparent, and is designed to be open and inclusive.

## Mission

DIIP aims to provide a comprehensive, community-driven specification for decentralized identity interoperability, fostering collaboration between implementers, vendors, and the
broader identity ecosystem.

## Governance Structure

### Specification Editors

Specification Editors are responsible for:

- **Technical oversight** of the specification
- **Review and approval** of Pull Requests
- **Merge authority** for contributions
- **Quality assurance** of the specification content
- **Release coordination** and timeline management

## Release Process

### 6-Month Release Cycle

DIIP operates on a structured 6-month release cycle:

1. **Development Phase** (Months 1-5):
    - Active development on the `develop` branch
    - Community contributions accepted via PRs
    - Regular reviews and feedback incorporation
    - Draft updates published continuously

2. **Release Preparation** (Month 6):
    - Feature freeze and stabilization
    - Final reviews and quality checks
    - Documentation and example verification
    - Community feedback integration

3. **Release Publication**:
    - Draft from `develop` branch promoted to `main`
    - New official DIIP version published
    - Community announcement and communication
    - Cycle reset for next version

### Version Access

- **Published Version**: Available at [https://FIDEScommunity.github.io/DIIP](https://FIDEScommunity.github.io/DIIP)
- **Draft Version**: Available at [https://FIDEScommunity.github.io/DIIP/draft](https://FIDEScommunity.github.io/DIIP/draft)

## Decision Making Process

### Pull Request Workflow

1. **Submission**: Anyone can submit a PR
2. **Community Review**: Open for public comment and discussion
3. **Editor Review**: Editors perform technical and quality review
4. **Preview Generation**: Automatic rendering for visual verification
5. **Approval**: Requires editor approval for merge
6. **Integration**: Merged into appropriate branch (`develop` for next version)

### Consensus Building

- **Rough Consensus**: Decisions aim for broad agreement, not unanimity
- **Editor Authority**: Final technical decisions rest with editors
- **Community Input**: All voices are heard and considered
- **Transparency**: Decision rationale is documented and communicated

## Project Organization

### Repository Structure

- **`main` branch**: Published specification versions
- **`develop` branch**: Active development and next version draft
- **`spec/` directory**: Core specification content
- **`assets/` directory**: Supporting files and examples

### Communication Channels

1. **GitHub Issues**: Bug reports, feature requests, formal discussions
2. **GitHub Pull Requests**: Direct contributions and code review
3. **GitHub Discussions**: High-level conversations and community feedback
4. **Discord**: Real-time community interaction and support

## Roles and Responsibilities

### Specification Editors

**Responsibilities:**

- Maintain technical quality and consistency
- Review and merge Pull Requests
- Coordinate release timeline and process
- Resolve conflicts and technical disputes
- Represent the specification in external forums

**Authority:**

- Final approval on all changes
- Branch merge permissions
- Release decision making
- Conflict resolution

### Community Contributors

**Rights:**

- Submit Pull Requests and Issues
- Participate in reviews and discussions
- Access to all project resources and documentation
- Recognition for contributions

**Responsibilities:**

- Follow contribution guidelines
- Respect community standards and code of conduct
- Provide constructive feedback
- Help maintain project quality

## Code of Conduct

All participants must adhere to professional and respectful behavior:

- **Inclusive Environment**: Welcome all backgrounds and perspectives
- **Constructive Feedback**: Focus on technical merit and specification improvement
- **Professional Conduct**: Maintain courtesy and respect in all interactions
- **Good Faith Participation**: Engage with genuine intent to improve the specification

## Governance Evolution

This governance model may evolve as the project grows:

- **Annual Review**: Governance effectiveness assessed yearly
- **Community Input**: Changes proposed and discussed openly
- **Editor Consensus**: Governance changes require editor agreement
- **Transparency**: All changes documented and communicated

## Contact and Support

For governance-related questions:

1. **Create an Issue** for formal discussions
2. **Start a Discussion** for broader community input
3. **Contact Editors** directly for urgent matters

## Amendment Process

To propose changes to this governance document:

1. Open a GitHub Issue describing the proposed changes
2. Allow for community discussion (minimum 2 weeks)
3. Submit a Pull Request with the specific changes
4. Require approval from majority of current editors
5. Announce changes to the community
